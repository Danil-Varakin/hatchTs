# Hatch

**Структурные семантические патчи для исходного кода.** Вместо хрупких номеров
строк патч Hatch описывает, *где* менять код, в терминах самой структуры кода — а
инструмент находит место. Порт оригинального Python-прототипа на TypeScript:
типизированный AST и npm-нативный пайплайн (без Python в сборке).

> English version: [README.md](./README.md)
> Архитектура: [ARCHITECTURE.md](./ARCHITECTURE.md) · Как участвовать: [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md)

---

## Зачем

Патчить быстро меняющийся upstream классическими `.patch`-файлами больно:
вставили пару строк выше — и номера строк во всех ханках поехали. Hatch описывает
изменение декларативно — «вставить вот это *после того include*, *внутри той
функции*» — тремя операторами. Позиция ищется по разобранной структуре файла,
поэтому переформатирование и несвязанные правки upstream патч не ломают.

Три команды:

- **`apply`** — применить `.md`-инструкции к исходному файлу.
- **`generate`** — сравнить две версии файла и породить `.md`-инструкции.
- **`grammars`** — положить грамматики tree-sitter на место (см. «Грамматики»).

`generate`, затем `apply` замыкают round-trip: применение порождённого патча к
старому файлу воспроизводит новый. `generate` гарантирует это по построению — он
применяет каждого кандидата настоящим патчером и оставляет только того, кто
воспроизвёл правку.

## Формат файла

Патч — это Markdown из пар блоков `match`/`patch`:

```
# match <язык>
    <шаблон, каждая строка с жёлобом в четыре пробела>
# end
# patch
    <текст замены, тот же жёлоб>
# end
```

Три правила, и это весь формат:

1. **Колонка 0 принадлежит структуре.** `# match`, `# patch` и `# end`
   распознаются только там.
2. **Каждая строка нагрузки несёт жёлоб в четыре пробела**, он снимается при
   чтении. Поэтому строка нагрузки физически не может попасть в колонку 0:
   ограда ` ``` `, заголовок `# patch` или `# end` внутри raw string — обычный
   текст. Разделителя, с которым код мог бы столкнуться, в формате нет вовсе.
3. **Блок закрывается `# end`.** Пустые строки внутри блока — нагрузка, включая
   хвостовые; пустые строки между ханками — нет. Всё до первого `# match` —
   свободная проза.

Строка нагрузки без жёлоба — ошибка разбора, а не тихая потеря. Единственное
исключение, которое стоит знать: строка со **значащими хвостовыми пробелами**
неотличима от мусора для любого whitespace-fix, поэтому не прогоняйте файл
инструкций через такой инструмент — `generate` предупреждает, когда печатает
такую строку.

## Язык: три оператора

Блок `match` пишется на целевом языке, операторы вставлены между строками:

| Оператор | Значение |
|----------|----------|
| `...`    | пропуск до следующего якоря (перебираются все вхождения, с откатами) |
| `>>>`    | точка вставки |
| `<<<`    | конец диапазона замены (он начинается от `>>>`) |

Всё, что не оператор, — **якорь-литерал**, кусок целевого файла, который обязан
там быть. Шаблон описывает файл **целиком**: нет `...` перед первым литералом —
значит «с самого начала файла», нет `...` после последнего — «до конца файла».

Пробелы между литералами и операторами для скобочных языков незначимы, поэтому
якоря можно копировать из исходника и переотступать как удобно. Для Python — нет:
ведущий отступ строки нагрузки входит в якорь, поэтому многострочный якорь
закрепляет уровень каждой своей строки. Питоньи якоря копируйте из исходника
вместе с отступом.

Оператор распознаётся только как отдельное *слово* (пробел или край строки с
обеих сторон), поэтому `template <typename... Args>` остаётся литералом.
Настоящее обособленное `...` в коде экранируется как `\...`.

**Внутри строкового литерала пробел — данные, и он значим.** `Log("a  b")` и
`Log("a b")` — разные якоря, второй на первом не сработает. Исключение —
МНОГОСТРОЧНЫЙ литерал (`R"(…)"`, докстринг, template literal, backtick в Go): внутри
него пробелы по-прежнему схлопываются. Причина в том, что якорь — фрагмент, отрезанный
по границам строк, и он может начаться внутри такого литерала, не имея возможности об
этом узнать; уравнять обе стороны можно только так.

## Примеры

Вставить вызов в конец тела функции:

```markdown
# match cpp
    ...
    void RegisterFeatures(FeatureList* list) {
      list->Add(kFastPath);
    >>>
    }
    ...
# end
# patch

      list->Add(kNewPath);
# end
```

Читается так: *пропусти что угодно, найди заголовок этой функции, затем этот
вызов, **вставь здесь**, а сразу следом обязана идти закрывающая `}` — дальше что
угодно до конца файла.* `}` здесь не украшение: именно она удерживает вставку
**внутри** этой функции (см. третье правило ниже).

Заменить диапазон — всё между `>>>` и `<<<` это старый код, он обязан совпасть и
в выход не идёт:

```markdown
# match cpp
    ...
    namespace content {
    ...
    >>>
    void RegisterFeatures( ... ) {
    <<<
    ...
# end
# patch
    // Registers every content feature.
    void RegisterFeatures( FeatureList* list ) {
# end
```

Обрати внимание на `...` **внутри** якоря: нутро сбалансированной скобочной пары
можно пропустить, и якорь переживёт правку списка аргументов. `generate` по
умолчанию так якоря и пишет.

## Установка

```bash
npm i -g https://github.com/Danil-Varakin/hatchTs/releases/download/v0.1.0/hatch-0.1.0.tgz
```

Появляется команда `hatch`. Грамматик внутри нет (~22 МБ на одиннадцать языков),
поэтому один раз после установки:

```bash
hatch grammars
```

Из клона репозитория работает и без установки — `npm run hatch -- <команда>`.

## Использование

```bash
# apply
hatch apply --match changes.md --in src/main.cpp --out src/main.cpp

# generate
hatch generate --in new.cpp --in-old old.cpp --out changes.md

# ...или взять старую версию из git-ветки
hatch generate --in src/main.cpp --branch master --out changes.md
```

`hatch` без аргументов печатает список команд, `hatch <команда> --help` — её опции,
`hatch --version` — версию инструмента и версию схемы конфига.

Коды выхода (на них можно опираться в скриптах):
`0` ок · `1` ошибка вызова · `2` разбор `.md` · `3` не легло · `4` неоднозначно ·
`5` конфиг · `6` грамматика.

### Опции `apply`
```

--in,    -i <файл>      исходник, который патчим                  [обязательно]
--out,   -o <файл>      куда писать результат   [обязателен, кроме --dry-run/--verify]
--language, -l <язык>   задать язык (иначе: `# match <язык>` в .md, иначе
                        расширение файла)
--dry-run               показать планируемые правки, ничего не писать
--verify                только код выхода (0 = ложится чисто), ничего не писать
--download-grammars     разрешить скачать грамматику языка, если её нет
                        (по умолчанию выключено, см. «Грамматики»)
--log [место]           писать полный лог; на каждый запуск свой файл, права 0600.
                        Место-директория (или со слешем на конце) получает
                        сгенерированное имя, иначе место И ЕСТЬ имя файла;
                        опущено — ./hatch-logs/
--help,  -h             эта справка
```

### Опции `generate`
```
--in,     -i <файл>     новая версия файла                        [обязательно]
--in-old     <файл>     старая версия (из файла)      [одно из --in-old/--branch]
--branch, -b <ветка>    старая версия = <ветка>:<путь из --in> (git)
--out,    -o <путь>     куда писать .md. Путь без расширения (а также с
                        завершающим слешем или указывающий на существующую папку) —
                        это ДИРЕКТОРИЯ, внутрь пишется <имя --in>.md; путь с
                        расширением — сам файл, перезаписывается. Недостающие папки
                        создаются. Относительный путь считается от корня
                        репозитория, а не от текущей папки. Опущен — рядом с --in;
                        `-` — писать в stdout
--mirror                держать патчи отдельным деревом: .md пишется в
                        <--out>/<путь --in внутри репозитория>.md, недостающие
                        папки создаются. Требует --out, который при этом всегда
                        читается как директория; относительный берётся от корня
                        репозитория, а не от текущей папки
--language,-l <язык>    задать язык (иначе: расширение --in)
--agreement,-a          подтверждать каждый ханк перед записью
--exact,  -e            воспроизвести новый файл байт в байт; без него каждая
                        строка обязана совпасть лишь после нормализации (отступы
                        и пробелы внутри строк свободны, состав строк — нет)
--debug,  -v            трейс синтеза в stderr: каждый сегмент, каждая проба
                        привязки (включая неуникальные) и выбранный ханк
--download-grammars     разрешить скачать грамматику языка, если её нет
                        (по умолчанию выключено, см. «Грамматики»)
--log [место]           писать полный лог: разрешённый конфиг с происхождением
                        каждого значения и весь трейс синтеза — независимо от -v.
                        На каждый запуск свой файл, права 0600; опущено —
                        ./hatch-logs/
--help,   -h            эта справка
```

#### Опции привязки (сколько контекста несёт ханк)
```
--parents <n|all>       потолок подъёма: не больше n охватывающих блоков
                        в шаблоне (по умолчанию: все)
--min-parents <n>       сколько охватывающих блоков несёт КАЖДЫЙ шаблон (1)
--parent-detail <n>     сколько уровней скобок остаётся дословно в заголовках
                        родителей, считая от внешней: 0 даёт `foo( ... )`,
                        1 — `foo(bar( ... ))` (0)
--min-siblings <n>      сколько соседних значащих строк несёт КАЖДЫЙ шаблон,
                        с каждой стороны (0)
--siblings <n>          потолок соседних значащих строк с каждой стороны (8);
                        0 запрещает опираться на соседей вовсе
--sibling-detail <n>        та же база для якорей-соседей (0)
--require-parents       не скатываться к шаблону без родителя: лучше отказ
--bridge-gap <n>        сшивать правки, разделённые не более чем n неизменёнными
                        непустыми строками, в один ханк (0)
```

Это размен двух видов отказа. Больше родителей и меньше соседей — привязка
**структурная**: она переживает правку соседних строк чужим коммитом, потому что
незакрытая `{` упорядочивает обход, а её закрывашка держит правку внутри блока.
Меньше родителей и больше соседей — якорь короче и читабельнее, но дрейфует.
Неоднозначность лечится сперва *деталью* (раскрытием скобок самого якоря) и лишь
потом соседями. Потолка раскрытия НЕТ: когда якорь неоднозначен, лестница сама
раскрывает по ОДНОЙ скобке — той, которая действительно сокращает число мест, где
якорь может начаться, — и останавливается, как только ни одна скобка не помогает.
Поэтому `detail` — одна ручка, а не пара.

`detail.base` — ручка ЧИТАЕМОСТИ: подняв её, во всех ханках внешние скобки
остаются дословными. Платится за это устойчивостью к дрейфу, а не корректностью:
более длинный якорь СПЕЦИФИЧНЕЕ, уникальность от него не страдает. Этот размен
из одной пары версий файла не измерить — потому он и политика, а не автоматика.

### Конфигурация

Всё перечисленное можно закрепить как политику проекта в `hatch.config.json`;
файл ищется **вверх по дереву от `--in`**, но только в пределах проекта: поиск
останавливается на корне репозитория (директория с `.git`) и никогда не заходит в
домашнюю директорию. Конфиг уровнем выше репозитория — это не та политика, на
которую соглашались, и по выводу этого не заметить. Слои, от
слабого к сильному:

```
встроенные дефолты  <  hatch.config.json  <  флаги CLI
```

```json
{
  "$schema": "./hatch.config.schema.json",
  "version": 1,
  "generate": {
    "out": "patches/",
    "language": "cpp",
    "exact": false,
    "bridgeGap": 0,
    "parents": {
      "min": 1,
      "max": "all",
      "detail": { "base": 0 },
      "required": false
    },
    "siblings": { "min": 1, "max": 8, "detail": { "base": 0 } },
    "out": "patches",
    "mirror": true
  }
}
```

`generate.out` — это МЕСТО, а не обязательно имя. Значение **без расширения** (а также с
завершающим слешем или указывающее на уже существующую папку) — это директория, внутрь
пишется `<имя --in>.md`; значение с расширением — сам файл. Недостающие папки создаются, а
файл, занявший имя нужной папки, называется по имени, а не превращается в `EEXIST … mkdir`.
Относительное значение считается от **корня репозитория**, а не от текущей папки: одни и
те же настройки обязаны означать одно и то же место в терминале, в редакторе (чья текущая
папка никого не касается) и в CI. Вне репозитория запасной вариант — папка патчуемого
файла. У `apply --out` правила те же.

`generate.mirror` превращает это место в дерево. При нём патч для
`chromium_src/browser/core/apdate.cc` попадает в
`<out>/chromium_src/browser/core/apdate.cc.md`, недостающие папки создаются, а `out`
обязателен и всегда читается как директория.

Пути отсчитываются от **корня репозитория** — ближайшей папки с `.git` вверх по дереву,
той же границы, на которой останавливается поиск конфига. Файл вне репозитория — ошибка,
а не догадка: зеркальный патч не может лечь в постороннее место. Относительный `out`
тоже берётся от этого корня, поэтому `hatch generate` из разных папок пишет в одно и то
же место.

```
--config <файл>         взять этот конфиг вместо поиска вверх по дереву; явный
                        путь ничем не ограничен — так один конфиг делится между
                        несколькими репозиториями
--no-config             игнорировать конфиг-файлы (только дефолты и флаги)
--print-config          напечатать итоговые настройки, файл, из которого они
                        взяты, и происхождение каждой
```

Настраивается только сторона **generate**. `.md`-патч — публичный контракт и
обязан значить одно и то же на любой машине, поэтому всё, что меняет ЧТЕНИЕ
готового патча (`apply`), в конфиг не выносится никогда — такое записывается
внутрь самого `.md`. Неизвестный ключ — ошибка (код `5`), а не молчаливый
дефолт.

Когда патч не ложится, быстрее всего понять причину так: `--debug` у `generate`
показывает, как выбирались якоря, а `--dry-run` у `apply` — какие ровно правки
получились бы, не трогая файл.

### Коды выхода (для CI)
`0` успех · `2` ошибка разбора · `3` нет совпадения (показывает «самую глубокую»
точку, до которой дошёл шаблон) · `4` неоднозначно (показывает конкурирующие
позиции) · `5` негодная конфигурация · `1` непредвиденное.

Неоднозначность — **ошибка**, а не молчаливый выбор: если шаблон ложится в двух
местах с разным результатом, будет код `4` и список позиций, а лечится это
добором контекста.

## API

```ts
import { applyAll, synthesize, parseHatchFile, printHatchFile, adapterForLanguage } from 'hatch';

const adapter = adapterForLanguage('cpp');
await adapter.init();

const { source, edits } = applyAll(oldCode, parseHatchFile(md), adapter);
const md2 = printHatchFile(synthesize(oldCode, newCode, adapter), 'cpp');
```

### Функции

| | |
|---|---|
| `applyAll(source, file, adapter)` | применяет ханки по очереди; возвращает `{ source, edits }`. Бросает `MatchError` или `AmbiguityError` на первом ханке, который не лёг |
| `synthesize(old, new, adapter, options?)` | порождает `Hunk[]` из двух версий файла |
| `parseHatchFile(text)` | `.md` → `HatchFile` |
| `printHatchFile(hunks, language?)` | `Hunk[]` → `.md` |
| `trailingSpaceWarnings(hunks)` | строки тела патча со значащими хвостовыми пробелами |
| `adapterForLanguage(name)` | адаптер по имени языка |
| `adapterForFile(path)` | адаптер по расширению файла |
| `supportedLanguages` | имена и синонимы языков реестра |

`adapter.init()` вызывается один раз и грузит грамматику; `buildMap` после этого
синхронный.

### Ошибки

`HatchError` — общий предок, у каждого наследника поле `exitCode`, совпадающее с
кодом выхода CLI: `ParseError` (2), `MatchError` (3), `AmbiguityError` (4),
`ConfigError` (5), `GrammarError` (6).

### Типы

`HatchFile`, `Hunk`, `MatchPattern`, `LanguageAdapter`, `ApplyResult`,
`AppliedEdit`, `SynthOptions`, `SynthEvent`, `Tracer`.

### Границы

Экспортируется только перечисленное выше. Матчер, патчер, канонизатор, карта
исходника, `infra/` и содержимое папок языков — внутренние и меняются без
предупреждения; подпути (`hatch/dist/...`) закрыты полем `exports`.

`LanguageAdapter` доступен как тип: адаптер получают из реестра и передают
обратно. Написание своих адаптеров не поддерживается.

## Грамматики

Разбор делает tree-sitter, поэтому каждому языку нужен свой `.wasm`. В репозитории
их **нет**: одиннадцать штук весят 22 МБ, а нужен почти всегда один. Вместо этого
язык пинует свою грамматику в собственной папке:

```ts
grammar: {
  file: 'tree-sitter-go.wasm',
  package: 'tree-sitter-go',
  version: '0.25.0',
  sha256: '9504573f352b20be7f2f1911754d710622aedc15afff16d5ed8fb5645681aee7',
},
```

Скачать один раз — это единственная команда, которая ходит в сеть намеренно:

```bash
hatch grammars
```

Файлы ложатся в общий пользовательский кеш (`~/.cache/hatch/grammars` или
платформенный аналог), так что другие клоны переиспользуют скачанное.

**Само по себе ничего не качается.** `.wasm` — исполняемый код, поэтому
отсутствующая грамматика это ошибка (код выхода `6`) с командой, которой она
чинится. Разрешить загрузку одному запуску — явно: `--download-grammars` или
`HATCH_GRAMMARS_DOWNLOAD=1` для CI. Когда загрузка разрешена, версия точная,
транспорт только https, а байты обязаны сойтись с записанным sha256 — расхождение
роняет запуск, а не уводит на другое зеркало.

| Переменная | Что делает |
|---|---|
| `HATCH_GRAMMAR_DIR` | искать сначала здесь — закрытый контур, своя сборка грамматики |
| `HATCH_GRAMMAR_CACHE` | куда складывать скачанное |
| `HATCH_GRAMMARS_DOWNLOAD=1` | разрешение качать, для CI |

`grammars` — такая же команда, как `apply` и `generate`, а не сборочный скрипт:
`hatch grammars --list` покажет, что зарегистрировано и где сейчас лежит,
`--language go` скачает одну грамматику, а `--pin <package@version>` напечатает блок
для вставки в `index.ts` нового языка.

## Три правила, зафиксированные волевым актом (из синтаксиса не выводятся)

Они осознанные и стабильные; патчи на них опираются:

1. **`<<<` заменяет ВКЛЮЧИТЕЛЬНО.** Литералы между `>>>` и `<<<` — это «старый
   код»: обязаны совпасть, но в выход не идут — их место занимает тело патча.
   Литералы *снаружи* меток — контекст, сохраняются.
2. **Шаблон описывает файл целиком.** `...` — единственный способ что-то
   пропустить. Нет ведущего `...` — первый якорь стоит со смещения 0; нет
   хвостового — последний якорь кончается на EOF.
3. **Незакрытая `{` упорядочивает, но не запирает.** Совпавшая открывающая скобка
   означает лишь «следующий якорь — после неё»: поиск всё равно идёт до конца
   файла, и «побег» из блока легален. Чтобы удержать правку **внутри**
   конструкции, в шаблоне надо написать её закрывающий токен. Поэтому `generate`
   выдаёт и заголовок охватывающей функции, и её `}`.

## Поддержка языков

Языки, на которых написан Chromium:

| Язык | Расширения | Имя в заголовке / `--language` |
|------|-----------|--------------------------------|
| C++ | `.cc` `.cpp` `.cxx` `.h` `.hpp` `.inc` | `cpp`, `c++`, `cc`, `cxx`, `h`, `hpp` |
| C | `.c` | `c` |
| Objective-C | `.m` `.mm` | `objc`, `objective-c` |
| Python | `.py` `.pyi` | `python`, `py` |
| JavaScript (с JSX) | `.js` `.mjs` `.cjs` `.jsx` | `javascript`, `js`, `jsx` |
| TypeScript | `.ts` `.mts` `.cts` | `typescript`, `ts` |
| TSX | `.tsx` | `tsx` |
| Rust | `.rs` | `rust`, `rs` |
| Java | `.java` | `java` |
| Kotlin | `.kt` `.kts` | `kotlin`, `kt` |
| Go | `.go` | `go`, `golang` |

Структура берётся из tree-sitter, поэтому ветки препроцессора, raw-строки, макросы
и дженерики (`Map<K, V>` — пара скобок, `a < b` — нет) не путают сопоставление.
`.h` считается C++ по конвенции Chromium. `.mm` — это Objective-C++, которого не
покрывает полностью ни одна грамматика tree-sitter: лучше всех справляется
грамматика Objective-C, а на чисто C++-участках структура беднеет до текстового
сопоставления.

### Как добавить язык: правило одной папки

**Язык — это одна папка в `src/lang/` и один `index.ts` в ней, где лежат ВСЕ его
правила: какую грамматику грузить, какие расширения считать своими, как
балансировать вложенность (`blockOf`) и как канонизировать текст литерала
(`normalize`). Правила языков НЕ выносятся в общий модуль — даже когда у двух
языков они записались бы дословно одинаково.**

Что это даёт: чтобы добавить язык, вы копируете одну папку и правите один файл,
ничего не зная про остальные и ничего в них не задевая. Видимое дублирование —
осознанная цена, и на практике правила расходятся: наборы скобочных пар у C, Go,
JavaScript и Python уже разные, а Kotlin требует своего определения того, где
начинается заголовок блока. Общий модуль «правил C-подобных» превратил бы каждое
такое различие в флаг.

Общим остаётся только язык-НЕЙТРАЛЬНОЕ: загрузка грамматики, обход дерева,
обвязка канона, сборка карты — то, чего язык не выбирает. Единственный общий файл,
который затрагивает добавление языка, — реестр адаптеров, и только потому, что
whitelist обязан быть статическим списком: имя языка приходит из недоверенного
`.md` и не должно превращаться в динамический импорт.

В `src/core/` при этом тоже не меняется ничего — это вторая проверка границы, и ни
одному языку из таблицы исключений не потребовалось. Python среди них стоит
особняком: значимый отступ, поэтому у него свой канонизатор и своё понятие блока,
где открывающий токен — двоеточие.

Грамматики лежат в `grammars/*.wasm` и копируются из официальных npm-пакетов
tree-sitter командой `hatch grammars`.

## Сборка и запуск

Исходники — `.ts`, исполняются напрямую на **Node 22+** через strip-types, поэтому
разработке шаг сборки не нужен. Пакет для публикации собирается (`npm run build` →
`dist/`), и именно эта сборка попадает в архив `npm pack`.

```bash
npm test          # юнит-, round-trip- и golden-наборы
npm run typecheck # tsc --noEmit по src/ и test/
npm run check     # то и другое
npm run build     # dist/, только для пакета
```

Разбор структуры — через **tree-sitter** (`web-tree-sitter`, WASM-грамматики:
кросс-платформенно, без нативной сборки); грузятся разово на старте. Рабочий
процесс и обоснование строгого tsconfig — в [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md).
