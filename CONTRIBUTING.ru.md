# Как участвовать

> English version: [CONTRIBUTING.md](./CONTRIBUTING.md)

Спасибо, что помогаешь делать Hatch. Этот файл — практическое «как с этим
работать»; обоснование дизайна — в [ARCHITECTURE.md](./ARCHITECTURE.md) (англ.).

## Что нужно

- **Node 22+** — исходники исполняются через strip-types, шага сборки нет.
- `npm install` ставит три рантайм-зависимости: `web-tree-sitter` (WASM-грамматики
  — кросс-платформенно, без компилятора и `node-gyp`), `diff` (построчный diff под
  `generate`) и `simple-git` (достать старую версию из ветки).
- Грамматики грузятся асинхронно: адаптер отдаёт `init(): Promise<void>`, его
  ждут разово на старте CLI, после чего `buildMap` синхронный. Всё, что зовёт
  `buildMap` — включая тесты, — обязано сначала сделать `await adapter.init()`.

## Запуск и проверки

```bash
npm test           # node --test по test/**/*.test.ts
npm run typecheck  # tsc --noEmit по src/ и test/ (два конфига)
npm run check      # и то и другое — гоняй перед каждым коммитом
```

CLI — обычные точки входа, их можно звать напрямую или через скрипты:

```bash
npm run apply -- --match changes.md --in src/main.cpp --out out.cpp
npm run generate -- --in new.cpp --in-old old.cpp --debug
```

Сейчас всё зелёное; так и держим. Красный `tsc` — коммит заблокирован.

## Строгий tsconfig (без причины не ослаблять)

Конфиг намеренно строгий, каждый флаг отрабатывает своё место:

- **`noEmit` + `allowImportingTsExtensions`** — tsc только проверяет типы;
  исходники исполняет `node --experimental-strip-types`, поэтому импорты пишутся
  с расширением `.ts`. Если однажды соберёшься собирать в `dist/` — верни опции
  эмита и добавь `rewriteRelativeImportExtensions` (переписывает `.ts`→`.js`).
- **`verbatimModuleSyntax` + `isolatedModules`** — импорты только типов ОБЯЗАНЫ
  быть `import type { … }`. Всё дерево написано так: типы из `ast.ts` через
  `import type`, значение `ParseError` — обычным `import`.
- **`noUncheckedIndexedAccess`** — доступ по индексу (`arr[i]`, `m.groups[k]`) даёт
  `T | undefined`. Обрабатывай явно (`?? ''`, `.entries()`, проверки или `!` там,
  где присутствие гарантировано инвариантом).
- **`exactOptionalPropertyTypes`** — `hint?: string` НЕ включает `undefined`;
  присваивай поле только когда значение есть (`if (hint !== undefined) …`). Если
  объект опций законно получает вычисленное `T | undefined` — расширь до
  `T | undefined` это одно поле, а не ослабляй флаг.

## Соглашения по коду

- **Никаких parameter properties в конструкторах** — strip-types их не понимает.
  Объявляй поля явно (см. `errors.ts`).
- `core/` остаётся язык-нейтральным. Если правка там «ради C++» или «ради
  Python» — ей место в адаптере под `lang/`. Это и есть проверка границы.
  Конкретно: ни одного `case '}'`, никаких правил отступов, никакого импорта
  tree-sitter в `core/`.
- Комментарий объясняет **почему**, а не что. Все сложные места здесь — неочевидные
  компромиссы; комментарий, пересказывающий код, — шум, а фиксирующий, какой
  отказ строка предотвращает, — окупается.
- Инвариант, который может нарушить баг, должен `throw`, а не тихо давать
  `undefined`. Плохой индекс, молча превратившийся в «весь файл», всплывает через
  три модуля от места ошибки.
- Атомарная запись файлов (`infra/fs.ts`): временный файл + `rename`. Инструмент
  правит исходники, обрезанный файл — сломанная сборка.
- Ошибки наследуют `HatchError` и несут `exitCode`. Сообщения пользователю — на
  английском и говорят, что делать дальше.
- Новый язык никогда не означает правку `core/`: добавь папку в `lang/` и две
  строки в реестр `lang/adapter.ts`. Реестр — закрытый whitelist: имя языка из
  `.md` никогда не превращается в динамический `import()`.

## Как устроен код

- `src/core/` — семантика Hatch, без знания языка: `ast.ts`, `errors.ts`,
  `hatch-parser.ts` (один проход, валидация по ходу), `hatch-printer.ts`,
  `matcher.ts`, `patcher.ts`.
- `src/lang/` — вся балансировка и нормализация: `source-map.ts` (центральный
  контракт), `adapter.ts` (реестр), общие `canon.ts` / `build-map.ts` /
  `block-spans.ts` / `treesitter.ts` и папки языков (`cpp/`, `python/`).
- `src/generate/` — обратный конвейер: `diff.ts` (атомарные сегменты правок),
  `synth.ts` (структурная привязка и проверка), `printer.ts` (сборка `.md`),
  `agreement.ts` (режим `-a`, чистое ядро — `confirm` приходит снаружи).
- `src/infra/` — побочные эффекты: атомарная запись, чтение файла из git-ветки.
- `src/cli/` — `apply.ts` и `generate.ts`, у каждого свой маленький разбор
  аргументов и `main()`, переводящий `HatchError` в код выхода.

## Тесты

- `test/unit/` — парсер, принтер, ошибки, матчер, патчер, source-map (проверяется
  **отдельно** от матчера), канон, нормализаторы языков, diff, synth, сквозной
  `generate`.
- `test/roundtrip/` — `parse(print(ast))` ≡ `ast`.

Что делает набор полезным:

- Тест проверяет **поведение вместе с причиной**, причина идёт в комментарий.
  Несколько тестов здесь существуют из-за конкретного прошлого бага — напиши,
  какого, чтобы потом никто не «упростил» ассерт.
- Для конвейеров предпочитай сквозные проверки: породить ханки, применить,
  сверить с ожидаемым файлом. Так ловится интерференция ханков, которую
  помодульные проверки не видят.
- Починил баг — добавь минимальный вход, который его воспроизводит, и убедись,
  что новый тест действительно падает на старом коде.

Инварианты из
[ARCHITECTURE.md](./ARCHITECTURE.md#diagnostics-and-invariants-green-on-every-commit)
должны быть зелёными на каждом коммите.

## Перед pull request

1. `npm run check` зелёный.
2. У нового поведения есть тест, у починенного бага — регрессионный.
3. Изменения публичного поведения отражены в `README.md` **и** `README.ru.md`, а
   текст `--help` совпадает с README.
4. Сообщение коммита говорит *почему*, а не только *что* поменялось.

## Грамматики

Грамматик в репозитории нет. Скачать один раз после `npm install`:

```bash
npm run grammars
```

`npm test` делает это сам (`pretest`), поэтому свежему клону нужна сеть на первом
прогоне тестов; дальше всё берётся из общего пользовательского кеша. Больше ничто
не качается само — см. раздел «Грамматики» в README.


## Релиз

Релиз выпускает **CI**, а не человек. Всё, что нужно, — поставить тег:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

Дальше `.github/workflows/release.yml` на чистой машине сверяет тег с `version` в
`package.json`, гоняет тайпчек и тесты, собирает `dist/`, делает `npm pack` и сам
создаёт GitHub Release с приложенным `.tgz`. Если тесты красные — релиза не будет.

Сверка тега с версией не даёт выпустить `v0.2.0` из кода, который считает себя
`0.1.0`: подняли версию в `package.json`, закоммитили, потом тег.

Локально архив можно собрать для проверки — ничего никуда не отправляя:

```bash
npm run pack
```

Посмотреть список файлов, ничего не создавая:

```bash
npm pack --dry-run
```

Внутри должны быть только `dist/`, оба README, `hatch.config.schema.json` и
`package.json` — список задаёт поле `files` в `package.json`. Ничего из `src/`,
`test/`, `docs/`.

Установка у пользователя:

```bash
npm i -g https://github.com/Danil-Varakin/hatchTs/releases/download/v0.1.0/hatch-0.1.0.tgz
```

Появляется команда `hatch`. Грамматик в архиве нет (~17 МБ на одиннадцать языков),
поэтому первый запуск скажет, что делать: `hatch grammars`.

Работает и установка прямо из репозитория (`npm i -g github:Danil-Varakin/hatchTs`) —
за это отвечает `prepare`, который собирает `dist/` уже на машине пользователя.

## Проверки (CI)

`.github/workflows/ci.yml` запускается на каждый push и pull request:

- **матрица** — Linux, macOS, Windows × Node 22 и 24, шесть комбинаций;
- **грамматики** кешируются между прогонами (`HATCH_GRAMMAR_CACHE` указывает на папку
  внутри рабочего каталога, её и запоминает `actions/cache`);
- **отдельная задача** собирает пакет и печатает его состав, чтобы лишний файл в
  `files` было видно до выкладки.

`test/golden` гоняется как часть `npm test`.

## Корпус и golden

`test/golden/` — 345 рукописных кейсов по одиннадцати языкам, они в репозитории и
гоняются обычным `npm test`. Проверяются ДВЕ разные вещи:

- **round-trip** — `synthesize → печать → разбор → apply → сверка с new`: результат
  корректен;
- **golden** — печатная форма `.md` сверяется с закоммиченным эталоном побайтово.
  Round-trip про форму не говорит ничего: ханк, переписывающий всё тело функции,
  воспроизводит файл так же честно, как однострочный.

Если правка ДОЛЖНА изменить печатную форму — пересоберите эталоны и **прочитайте
диф**:

```bash
UPDATE_GOLDEN=1 npm test
```

Два маркера в первой строке исходника кейса:

- `MUST-REFUSE` — инструкция обязана НЕ лечь (молчаливое ложное совпадение — худший
  класс бага, и на него нужен тест);
- `KNOWN-GAP` — синтез пока не умеет, и это записано намеренно. Почините — тест
  упадёт со словами «работает, уберите маркер».

Отдельно Hatch обкатывался на настоящих файлах chromium с настоящими патчами brave.
Этот материал — чужой код под чужой лицензией, в репозиторий он не входит; набор,
который может прогнать каждый, — `test/golden`.
