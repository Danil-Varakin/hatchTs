# Hatch

**Структурные семантические патчи для исходного кода.** Вместо хрупких номеров
строк патч Hatch описывает, *где* менять код, в терминах самой структуры кода — а
инструмент находит место. Порт оригинального Python-прототипа на TypeScript:
типизированный AST и npm-нативный пайплайн (без Python в сборке).

> English version: [README.md](./README.md)
> Архитектура: [ARCHITECTURE.md](./ARCHITECTURE.md) · Как участвовать: [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md)

## Зачем

Патчить быстро меняющийся upstream классическими `.patch`-файлами больно:
вставили пару строк выше — и номера строк во всех ханках поехали. Hatch описывает
изменение декларативно — «вставить вот это *после того include*, *внутри той
функции*» — тремя операторами. Позиция ищется по разобранной структуре файла,
поэтому переформатирование и несвязанные правки upstream патч не ломают.

Четыре команды:

- **`apply`** — применить `.hatch`-инструкции к исходному файлу.
- **`generate`** — сравнить две версии файла и породить `.hatch`-инструкции.
- **`grammars`** — положить грамматики tree-sitter на место (см. «Грамматики»).
- **`init`** — создать `hatch.config.json` (см. «Конфигурация»).

`generate`, затем `apply` замыкают round-trip: применение порождённого патча к
старому файлу воспроизводит новый. `generate` гарантирует это по построению — он
применяет каждого кандидата настоящим патчером и оставляет только того, кто
воспроизвёл правку.

## Формат файла

Патч — это файл `.hatch`: шапка, затем пары блоков `match`/`patch`:

```
Hatch: 1
Target: src/a.cc
Generated-From: 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
Generated-By: hatch 0.4.0
Grammar: tree-sitter-cpp@0.23.4

# match <язык>
    <шаблон, каждая строка с жёлобом в четыре пробела>
# end
# patch
    <текст замены, тот же жёлоб>
# end
```

Три правила, и это весь формат:

1. **Колонка 0 принадлежит структуре.** `# match`, `# patch` и `# end`
   распознаются только там.
2. **Каждая строка нагрузки несёт жёлоб в четыре пробела**, он снимается при
   чтении. Поэтому строка нагрузки физически не может попасть в колонку 0:
   ограда ` ``` `, заголовок `# patch` или `# end` внутри raw string — обычный
   текст. Разделителя, с которым код мог бы столкнуться, в формате нет вовсе.
3. **Блок закрывается `# end`.** Пустые строки внутри блока — нагрузка, включая
   хвостовые; пустые строки между ханками — нет. Всё до первого `# match` —
   свободная проза.

Шапка — строки `Имя: значение` до первой пустой строки, как в патчах Debian. Первой
идёт `Hatch` — номер формата; `Target` — файл, для которого патч, от корня репозитория;
`Generated-From` — blob в git, против которого он сделан; `Generated-By` и `Grammar` —
чем сделан. Пишет их `generate`; `apply` проверяет только `Hatch` (патч новее этого
hatch отклоняется с «обновите hatch») и `Target` (без `..`, не абсолютный). Незнакомые
поля пропускаются.

У полей постоянные места, в таком порядке:

| # | поле | когда пишется | |
|---|---|---|---|
| 1 | `Hatch` | всегда | номер формата, всегда первая строка |
| 2 | `Target` | когда у патча есть место | файл от корня репозитория, через `/` |
| 3 | `Generated-From` | когда база из git | blob базы в git |
| 4 | `Generated-By` | всегда | `hatch <версия>` |
| 5 | `Grammar` | всегда | `<пакет>@<версия>` |

Пропущенное поле не сдвигает остальные; известное поле не на своём месте или
повторённое — ошибка разбора. Незнакомые поля могут стоять где угодно после `Hatch`.
Новое поле добавляется только в конец списка (VERSIONING.md H4), поэтому шапка,
записанная старым hatch, читается новым так же. Файл без шапки — патч, написанный руками, — формат 1. hatch 0.3 и
старше писал `.md`: такой патч переименуйте (`git mv x.md x.hatch`) — ханки те же.

У ханка может быть комментарий: блок `# note` … `# end` прямо перед его `# match`.
Заметка — проза, в любой колонке, без жёлоба; её читают только люди, сопоставитель —
никогда; через сервис она приходит полем `note` ханка. Текст между ханками вне заметки —
ошибка разбора. `generate` заметок не пишет: повторный запуск поверх `.hatch` заменяет их
вместе со всем остальным.

```
# note
WAIT: без него драйвер зависает на полном буфере.
# end
# match c
    ...
```

Строка нагрузки без жёлоба — ошибка разбора, а не тихая потеря. Единственное
исключение, которое стоит знать: строка со **значащими хвостовыми пробелами**
неотличима от мусора для любого whitespace-fix, поэтому не прогоняйте файл
инструкций через такой инструмент — `generate` предупреждает, когда печатает
такую строку.

Окончания строк — не нагрузка. Файл инструкций может прийти с LF или с CRLF (git и
редакторы переводят их в обе стороны), читается он одинаково. Патч берёт окончание
строк того файла, в который ложится: в CRLF-файле каждая записанная им строка
кончается на CRLF, в LF-файле он ложится байт в байт. Если в файле окончания
смешаны, решает строка, с которой начинается правка.

## Язык: три оператора

Блок `match` пишется на целевом языке, операторы вставлены между строками:

| Оператор | Значение |
|----------|----------|
| `...`    | пропуск до следующего якоря (перебираются все вхождения, с откатами) |
| `>>>`    | точка вставки |
| `<<<`    | конец диапазона замены (он начинается от `>>>`) |

Всё, что не оператор, — **якорь-литерал**, кусок целевого файла, который обязан
там быть. Шаблон описывает файл **целиком**: нет `...` перед первым литералом —
значит «с самого начала файла», нет `...` после последнего — «до конца файла».

Пробелы между литералами и операторами для скобочных языков незначимы, поэтому
якоря можно копировать из исходника и переотступать как удобно. Для Python — нет:
ведущий отступ строки нагрузки входит в якорь, поэтому многострочный якорь
закрепляет уровень каждой своей строки. Питоньи якоря копируйте из исходника
вместе с отступом.

Оператор распознаётся только как отдельное *слово* (пробел или край строки с
обеих сторон), поэтому `template <typename... Args>` остаётся литералом.
Настоящее обособленное `...` в коде экранируется как `\...`.

**Внутри строкового литерала пробел — данные, и он значим.** `Log("a  b")` и
`Log("a b")` — разные якоря, второй на первом не сработает. Исключение —
МНОГОСТРОЧНЫЙ литерал (`R"(…)"`, докстринг, template literal, backtick в Go): внутри
него пробелы по-прежнему схлопываются. Причина в том, что якорь — фрагмент, отрезанный
по границам строк, и он может начаться внутри такого литерала, не имея возможности об
этом узнать; уравнять обе стороны можно только так.

## Примеры

Вставить вызов в конец тела функции:

```markdown
# match cpp
    ...
    void RegisterFeatures(FeatureList* list) {
      list->Add(kFastPath);
    >>>
    }
    ...
# end
# patch

      list->Add(kNewPath);
# end
```

Читается так: *пропусти что угодно, найди заголовок этой функции, затем этот
вызов, **вставь здесь**, а сразу следом обязана идти закрывающая `}` — дальше что
угодно до конца файла.* `}` здесь не украшение: именно она удерживает вставку
**внутри** этой функции (см. третье правило ниже).

Заменить диапазон — всё между `>>>` и `<<<` это старый код, он обязан совпасть и
в выход не идёт:

```markdown
# match cpp
    ...
    namespace content {
    ...
    >>>
    void RegisterFeatures( ... ) {
    <<<
    ...
# end
# patch
    // Registers every content feature.
    void RegisterFeatures( FeatureList* list ) {
# end
```

Обрати внимание на `...` **внутри** якоря: нутро сбалансированной скобочной пары
можно пропустить, и якорь переживёт правку списка аргументов. `generate` по
умолчанию так якоря и пишет.

## Установка

Требования: **Node.js 22 или новее**; **git** — только чтобы читать версию файла из
репозитория (`--head`, `--branch`, `--commit`, `--repo-path`, `baseGit` у сервиса).
Linux, macOS и Windows проверяются в CI.

К каждому релизу на [странице Releases](https://github.com/Danil-Varakin/hatchTs/releases)
приложен `hatch-<версия>.tgz`; установите этот архив по его адресу:

```bash
npm i -g https://github.com/Danil-Varakin/hatchTs/releases/download/v<версия>/hatch-<версия>.tgz
```

Появляется команда `hatch`, и грамматики tree-sitter всех языков уже внутри неё: после
установки ничего докачивать не нужно, и ничего никогда не скачивается.

Из клона репозитория работает и без установки — `npm run hatch -- <команда>`.

## Использование

```bash
# apply
hatch apply --match changes.hatch --in src/main.cpp --out src/main.cpp

# ...или пропатчить файл таким, каким его держит git: ляжет ли патч на master?
hatch apply --match changes.hatch --in src/main.cpp --branch master --verify

# generate
hatch generate --in new.cpp --in-old old.cpp --out changes.hatch

# ...или взять старую версию из git: тот же файл на момент последнего коммита
hatch generate --in src/main.cpp --head --out changes.hatch

# ветка (её последний коммит), конкретный коммит, другой путь внутри репозитория
hatch generate --in src/main.cpp --branch master --out changes.hatch
hatch generate --in src/main.cpp --commit 1f3ac9d --out changes.hatch
hatch generate --in src/main.cpp --branch master --commit 1f3ac9d \
               --repo-path src/legacy/main.cpp --out changes.hatch

# hatch.config.json в корне репозитория
hatch init
```

`hatch` без аргументов печатает список команд, `hatch <команда> --help` — её опции,
`hatch --version` — версию инструмента и версию схемы конфига.

Коды выхода (на них можно опираться в скриптах):
`0` ок · `1` ошибка вызова или иной отказ · `2` разбор `.hatch` · `3` не легло ·
`4` неоднозначно · `5` конфиг · `6` грамматика · `7` нет изменений · `8` не привязать
правку (подробно — в «Кодах выхода» ниже).

### Опции `apply`
```
--match, -m <файл.hatch>   инструкции (ханки match/patch)            [обязательно]
--in,    -i <файл>      исходник, который патчим                  [обязательно]
                        читается с диска, если не названа git-координата
--head,   -H            файл таким, каким его держит git — те же четыре флага,
--branch, -b <ветка>    с теми же умолчаниями, вопросами и отказами, что у `generate`
--commit, -c <коммит>   (см. «Откуда берётся старая версия» ниже)
--repo-path  <путь>
--out,   -o <файл>      куда писать результат   [обязателен, кроме --dry-run/--verify]
                        те же правила размещения, что у `generate --out`, кроме
                        дерева апстрима: директория получает <имя --in> внутри,
                        любой другой путь пишется как есть, недостающие
                        директории создаются, `-` пишет в stdout
--language, -l <язык>   задать язык (иначе: `# match <язык>` в .hatch, иначе
                        расширение файла)
--dry-run               показать планируемые правки, ничего не писать
--verify                только код выхода (0 = ложится чисто), ничего не писать.
                        Проверка — против чистой базы из git: флаги выше, иначе
                        generate.base; без них в терминале спрашивается, чистая ли
                        база файлы на диске, без терминала — отказ
--base-from-disk        --verify против файлов на диске, без вопроса
--config <файл>         конфиг вместо найденного вверх от патча;
--no-config             без конфига (тогда --in обязателен)
--download-grammars     с 0.4 ничего не делает — грамматики внутри hatch — и
                        предупреждает; удаляется в 0.5
--log [место]           писать полный лог; на каждый запуск свой файл, права 0600.
                        Место-директория (или со слешем на конце) получает
                        сгенерированное имя, иначе место И ЕСТЬ имя файла;
                        опущено — ./hatch-logs/
--yes,    -y            заранее ответить «да» на каждый вопрос (см. «Когда hatch
                        спрашивает, прежде чем продолжить» ниже)
--help,  -h             эта справка
```

С git-координатой `--in` перестаёт быть содержимым файла и становится его **именем**:
по нему ищется репозиторий, берётся путь по умолчанию внутри него и называется
результат — поэтому на диске его может не быть вовсе. Результат называется по `--in`,
даже когда `--repo-path` прочитал другой путь: это случай «пропатчить версию до
переименования и сохранить под новым именем».

Одно правило — только у `apply`. Записать результат поверх самого `--in`, когда
содержимое пришло из git, значит положить пропатченную git-версию на место рабочего
файла. Если при этом потеряется то, что в рабочем файле есть, сначала **спросят**
(см. «Когда hatch спрашивает»). Не спрашивают, когда терять нечего: в рабочем файле и
так был git-текст, или результат и есть рабочий файл (патч, сделанный из него же,
применён обратно). Патч на месте с диска это правило не затрагивает. Файл, в котором
результат уже лежит, не записывается вовсе (`already so: not written`): его время
изменения остаётся прежним, и сборка не перекомпилирует его.

Главный случай для этого — CI: `--verify --branch main` отвечает «ложится ли патч на
main», ничего не вычекивая.

                        текущая ветка, её последний коммит, путь из --in

                        Сама по себе означает последний коммит этой ветки.

--language,-l <язык>    задать язык (иначе: расширение --in)
--agreement,-a          показывать каждый ханк по мере синтеза: Enter оставляет;

                        закрывшийся раньше, останавливает запуск без .hatch

--debug,  -v            трейс синтеза в stderr: каждый сегмент, каждая проба
                        привязки (включая неуникальные) и выбранный ханк

--log [место]           писать полный лог: разрешённый конфиг с происхождением
                        каждого значения и весь трейс синтеза — независимо от -v.
                        На каждый запуск свой файл, права 0600; опущено —

--help,   -h            эта справка

#### Откуда берётся старая версия

Источник ровно один, и это не список режимов: либо файл на диске (`--in-old`),
либо git. Из git версия задаётся тремя **независимыми координатами**, и любую из
них можно не указывать — недостающая берётся по умолчанию:

| координата | флаг | если не указана |
|---|---|---|
| ветка  | `--branch` | та, в которой мы сейчас |
| коммит | `--commit` | последний коммит этой ветки |
| путь   | `--repo-path` | путь из `--in` внутри репозитория |

Все три опущены — это «тот же самый файл на момент последнего коммита здесь»; а
раз при этом не названо ни одной координаты, для обращения к git нужен свой флаг:
`--head`. Остальные сочетания выводятся из таблицы: `--branch master` — последний
коммит `master`, `--commit 1f3ac9d` — тот же файл из этого коммита, `--repo-path`
подменяет файл, не трогая коммит, из которого он читается.

Коммит называет версию сам по себе, поэтому `--commit 1f3ac9d` берётся как есть — где
бы этот коммит ни лежал. Ветка рядом с ним — это **утверждение о нём**, а утверждение
стоит проверить: отсюда `--branch` вместе с `--commit` — единственное сочетание,
способное себе противоречить. О коммите, которого в ветке никогда не было, спросят,
прежде чем читать версию из чужой истории.

Каждая координата отвечает и за свой РОД. `--branch` принимает **ветку** (локальную
или удалённую); о теге или голом sha спросят, указав на `--commit`, который принимает
любую понятную git ревизию. `--repo-path` принимает **файл**: каталог получает отказ,
а не выдаётся в виде напечатанного листинга дерева.

`--in-old` всё это не затрагивает: старая версия, не лежащая ни в каком
репозитории, остаётся путём на диске и останется им. В этом же и разница между двумя
«путевыми» флагами: `--in-old` — путь, который дополнит ваша оболочка, `--repo-path` —
путь, который найдёт git.

#### Ханк вручную

Когда синтез не может привязать правку — например, два одинаковых места, — а за
терминалом человек, `generate` не просто падает: он говорит почему и предлагает
редактор (`$VISUAL`, иначе `$EDITOR`, иначе `vi` / `notepad`). В редактор приходит
`.hatch` на этот момент — **все** ханки, заготовка для нужной правки и сама правка,
процитированная сверху. Всё, что вернётся, — и шаблон, и тело патча — проверяется:
файл должен разобраться, и каждый ханк должен лечь на старую версию по порядку. Если
нет — причина встаёт сверху, и вас спрашивают снова, сколько потребуется; ответ «нет»
останавливает запуск без `.hatch` (отредактированный файл сохраняется, путь печатается).
Когда всё сходится, синтез продолжается от текста, который дают эти ханки. Тело патча,
отредактированное так, что оно расходится с `--in`, остаётся как есть, а запуск
кончается предупреждением, что `.hatch` не даёт `--in`.

Без терминала — скрипт, CI — ошибка та же, что была всегда, с тем же кодом выхода.

#### Когда hatch спрашивает, прежде чем продолжить

Есть запросы, которые git выполнить может, но которые, возможно, говорят не то, что
имелось в виду. О них **спрашивают**, а не отказывают: предупреждение говорит, что
значит продолжить, и решает ответ:

| ситуация | продолжить значит |
|---|---|
| `--commit` не лежит в названной рядом `--branch` | коммит всё равно читается, из истории, которой у ветки не было |
| `--branch` называет тег или голый sha | он читается как обычная ревизия, как это сделал бы `--commit` |
| `apply` пишет поверх `--in`, чьё содержимое пришло из git, а в файле есть правки, которых в той версии нет | на его место ложится пропатченная git-версия; всё незакоммиченное в нём теряется |

```
warning: commit 1f3ac9d is not on branch main — going ahead reads that commit all the
same, out of a history branch main never had
  go ahead? [y/N]
```

По умолчанию — **нет**. `--yes` / `-y` отвечает «да» заранее, для скриптов. Когда
ответить некому — труба, CI, — ответ «нет», и запуск останавливается, сообщив, что с
`--yes` он бы продолжил. Запуск, за которым никто не смотрит, не должен быть тем, что
молча выбрасывает работу.

То, что git не может выполнить вовсе — ветки, коммита или файла нет, каталог на месте
файла, git не запускается, — вопросом не бывает никогда: продолжать не с чем, и
`--yes` этого не меняет.

#### Опции привязки (сколько контекста несёт ханк)
```
--parents <n|all>       потолок подъёма: не больше n охватывающих блоков
                        в шаблоне (по умолчанию: все)
--min-parents <n>       сколько охватывающих блоков несёт КАЖДЫЙ шаблон (1)
--parent-detail <n>     сколько уровней скобок остаётся дословно в заголовках
                        родителей, считая от внешней: 0 даёт `foo( ... )`,
                        1 — `foo(bar( ... ))` (0)
--min-siblings <n>      сколько соседних значащих строк несёт КАЖДЫЙ шаблон,
                        с каждой стороны (0)
--siblings <n>          потолок соседних значащих строк с каждой стороны (8);
                        0 запрещает опираться на соседей вовсе
--sibling-detail <n>        та же база для якорей-соседей (0)
--require-parents       не скатываться к шаблону без родителя: лучше отказ
--bridge-gap <n>        сшивать правки, разделённые не более чем n неизменёнными
                        непустыми строками, в один ханк (0)
```

Это размен двух видов отказа. Больше родителей и меньше соседей — привязка
**структурная**: она переживает правку соседних строк чужим коммитом, потому что
незакрытая `{` упорядочивает обход, а её закрывашка держит правку внутри блока.
Меньше родителей и больше соседей — якорь короче и читабельнее, но дрейфует.
Неоднозначность лечится сперва *деталью* (раскрытием скобок самого якоря) и лишь
потом соседями. Потолка раскрытия НЕТ: когда якорь неоднозначен, лестница сама
раскрывает по ОДНОЙ скобке — той, которая действительно сокращает число мест, где
якорь может начаться, — и останавливается, как только ни одна скобка не помогает.
Поэтому `detail` — одна ручка, а не пара.

`detail.base` — ручка ЧИТАЕМОСТИ: подняв её, во всех ханках внешние скобки
остаются дословными. Платится за это устойчивостью к дрейфу, а не корректностью:
более длинный якорь СПЕЦИФИЧНЕЕ, уникальность от него не страдает. Этот размен
из одной пары версий файла не измерить — потому он и политика, а не автоматика.

### Конфигурация

Всё перечисленное можно закрепить как политику проекта в `hatch.config.json`;
файл ищется **вверх по дереву от `--in`**, но только в пределах проекта: поиск
останавливается на корне репозитория (директория с `.git`) и никогда не заходит в
домашнюю директорию. Конфиг уровнем выше репозитория — это не та политика, на
которую соглашались, и по выводу этого не заметить. Если так ничего не нашлось, берётся
конфиг, который **заявляет** файл — его `"upstream"` содержит этот файл (см. «Проект поверх
чужого кода» ниже), затем `$HATCH_CONFIG`, затем конфиг в текущей папке, если он заявляет
файл. `--config` важнее всего этого. Слои, от слабого к сильному:

```
встроенные дефолты  <  hatch.config.json  <  флаги CLI
```

`hatch init` создаёт такой файл: только `"$schema"` и `"version"`, так что все
значения по умолчанию остаются встроенными, пока их не задать.

| опция | |
|---|---|
| `--config-version <n>` | версия схемы конфига; по умолчанию самая новая, которую читает этот hatch (`hatch --version`). О более старой будет строка в stderr |
| `--dir <папка>` | куда писать; по умолчанию корень git-репозитория от текущей папки, вне репозитория — сама папка |
| `--upstream <путь>` | проект правит чужой код: пишет `"upstream"` (от папки конфига) и `generate.out` (`--out`, по умолчанию `patches`); несуществующий апстрим — отказ |
| `--force` | заменить существующий `hatch.config.json` — без него файл не трогается, код выхода 5 |
| `--dry-run` | напечатать файл в stdout, ничего не записывая |

`"$schema"` указывает на JSON Schema именно этой версии,
`schemas/hatch.config.v<N>.schema.json`: редактор проверяет файл v1 по схеме v1, а не по
самой новой. Ключи файла сверяются с версией, которую он называет.

#### Как написать конфиг

Файл — обычный JSON: без комментариев и без висячих запятых. Пишите только то, что должно
отличаться от умолчания: ключ, которого нет, остаётся встроенным, и если следующая версия
hatch улучшит умолчание, ваш проект его получит. Все ключи и флаг, который перекрывает
каждый на один запуск:

| ключ | значение | по умолчанию | флаг | что делает |
|---|---|---|---|---|
| `$schema` | URL | — | — | только для редактора: подсказки и проверка при вводе. hatch его не читает |
| `version` | `2` | самая новая, что читает hatch | — | схема, по которой написан файл. Пишите её: ключи проверяются по своей версии |
| `upstream` | путь или `null` | `null` | `init --upstream` | корень кода, который проект правит, но которым не владеет, **от папки конфига**. С ним `generate.out` обязан быть папкой, а дерево патчей повторяет путь каждого файла от этого корня (см. «Проект поверх чужого кода») |
| `generate.out` | путь или `null` | `null` — рядом с `--in` | `--out` | куда пишется `.hatch`. Папка (`patches`, `patches/`) получает `<имя --in>.hatch`; имя на `.hatch` — сам файл; иное отклоняется. Относительный путь — от корня репозитория |
| `generate.language` | имя языка или `null` | `null` — по расширению `--in` | `--language` | для файлов, у которых расширение ничего не говорит или говорит не то (`.h` с кодом на C) |
| `generate.exact` | `true` / `false` | `false` | `--exact` | воспроизводить новый файл байт в байт. Без него отступы и пробелы внутри строки свободны, набор строк — нет |
| `generate.bridgeGap` | 0–1000 | `0` | `--bridge-gap` | две правки, между которыми не больше стольких неизменённых непустых строк, становятся одним ханком |
| `generate.parents.min` | 0–1000 | `1` | `--min-parents` | сколько охватывающих блоков (функция, класс, namespace) называет каждый шаблон. `0` разрешает шаблон без структуры |
| `generate.parents.max` | 0–1000 или `"all"` | `"all"` | `--parents` | как высоко шаблону можно подниматься, когда нужно больше контекста |
| `generate.parents.detail.base` | 0–1000 | `0` | `--parent-detail` | сколько уровней скобок раскрыто в этих заголовках, считая снаружи: `0` даёт `foo( ... )`, `1` — `foo(bar( ... ))` |
| `generate.parents.required` | `true` / `false` | `false` | `--require-parents` | падать, а не отступать к шаблону без охватывающего блока |
| `generate.siblings.min` | 0–1000 | `0` | `--min-siblings` | сколько соседних строк каждый шаблон цитирует с каждой стороны правки |
| `generate.siblings.max` | 0–1000 | `8` | `--siblings` | не больше стольких соседей с каждой стороны; `0` — на соседей не опираться вовсе |
| `generate.siblings.detail.base` | 0–1000 | `0` | `--sibling-detail` | как `parents.detail.base`, для соседних строк |
| `generate.base.head` | `true` / `false` | `false` | `--head` | старая версия из git: последний коммит текущей ветки |
| `generate.base.branch` | ветка или `null` | `null` — текущая | `--branch` | старая версия — вершина этой ветки (локальной или remote-tracking) |
| `generate.base.commit` | ревизия или `null` | `null` — вершина | `--commit` | старая версия — этот коммит: sha, тег, `HEAD~3` |
| `generate.base.eol` | `"repository"` / `"worktree"` | `"repository"` | `--eol` | окончания строк версии из git: как хранит git или как у файла на диске (`core.autocrlf`) |

Любой из `generate.base.head`, `branch`, `commit` означает «из git»; git-флаг в командной
строке на этот запуск заменяет все три, а `--in-old` их не смотрит. Числа — целые и не
отрицательные; ключ, которого нет в схеме, или значение не того вида останавливают
запуск с кодом 5 и называют ключ.

Конфиги для обычных случаев:

```json
{ "version": 2, "generate": { "base": { "head": true } } }
```

Патчи рядом со своими файлами, старая версия — всегда последний коммит:
`hatch generate --in src/a.cc` пишет `src/a.cc.hatch`.

```json
{ "version": 2, "upstream": ".", "generate": { "out": "patches", "base": { "branch": "main" } } }
```

Один репозиторий, все патчи отдельным деревом, сравнение с `main`:
`src/net/http.cc` → `patches/src/net/http.cc.hatch`.

```json
{
  "version": 2,
  "generate": {
    "out": "patches/",
    "base": { "head": true, "eol": "worktree" },
    "parents": { "min": 2, "detail": { "base": 1 } },
    "siblings": { "max": 2 }
  }
}
```

Все патчи в одной плоской папке; Windows с `core.autocrlf=true`; якоря всегда называют два
охватывающих блока с раскрытыми аргументами и опираются не больше чем на две соседние
строки — патчи длиннее, зато переживают правки апстрима в строках вокруг.

Посмотреть, что применится и откуда взялось каждое значение, ничего не генерируя:

```bash
hatch generate --in src/a.cc --print-config
```

`$schema` нужен только редактору: подсказки и проверка, пока вы пишете. Для каталога
SchemaStore схема тоже подготовлена (`.github/schemastore/`); когда hatch будет там в
списке, VS Code и JetBrains найдут её по имени файла, без этой строки. Сам hatch
`$schema` не читает — он проверяет весь файл при каждом запуске и называет любой
незнакомый ключ.

`generate.out` — это МЕСТО, а не обязательно имя. Значение **без расширения** (а также с
завершающим слешем или указывающее на уже существующую папку) — это директория, внутрь
пишется `<имя --in>.hatch`; значение с расширением — сам файл. Недостающие папки создаются, а
файл, занявший имя нужной папки, называется по имени, а не превращается в `EEXIST … mkdir`.
Относительное значение считается от **корня репозитория**, а не от текущей папки: одни и
те же настройки обязаны означать одно и то же место в терминале, в редакторе (чья текущая
папка никого не касается) и в CI. Вне репозитория запасной вариант — папка патчуемого
файла. У `apply --out` правила те же.

Значение, называющее файл, должно кончаться на `.hatch`; иное отклоняется до того, как
прочитан хоть один файл. Что делает `generate` при разных `--out`:

| `--out` | куда пишет патч | `Target` |
|---|---|---|
| не задан | рядом с `--in`: `<in>.hatch` | от корня репозитория |
| `-` | stdout | — |
| `patches`, `patches/`, существующая папка | `<корень репо>/patches/<имя --in>.hatch` | от корня репозитория |
| `p.hatch`, `deep/p.hatch` | этот файл, от корня репозитория | от корня репозитория |
| `p.md`, `p.txt` | отказ, код 5 | — |
| абсолютный путь | как выше, от `/` | нет, если патч вне репозитория |
| с `"upstream"` и папкой | `<папка конфига>/<out>/<путь от апстрима>.hatch` | от корня апстрима |
| с `"upstream"` и `-` или без `out` | отказ, код 5 | — |

Если в вычисленном месте уже лежит патч **другого** файла (два файла с одним именем в
плоском `out`), hatch сначала спрашивает: `--yes` — продолжить, без терминала — отказ с
кодом 5. Патч того же файла и файл, названный прямо (`--out x.hatch`), перезаписываются.

### Проект поверх чужого кода

Форк держит патчи в своём репозитории и правит код, в который сам не коммитит. Пусть
апстрим выкачан в `work/`, а проект лежит внутри него:

```
work/                         апстрим — репозиторий, куда вы не коммитите
├── src/ui/window.cc
├── third_party/zlib/         внутри — отдельный репозиторий
└── myfork/                   ваш проект — ваш репозиторий
    ├── hatch.config.json
    └── patches/
```

`work/myfork/hatch.config.json` говорит, где этот код:

```json
{ "version": 2, "upstream": "..", "generate": { "out": "patches", "base": { "head": true } } }
```

`upstream` — корень правимого кода **от файла конфига**. С ним патч для
`work/src/ui/window.cc` — это `work/myfork/patches/src/ui/window.cc.hatch`, а его
`Target` — `src/ui/window.cc`. База берётся из git-репозитория, ближайшего к файлу:
`work/third_party/zlib/...` читается из собственного репозитория zlib, без списка
репозиториев.

```bash
hatch generate --in work/src/ui/window.cc                   # найдёт конфиг myfork
hatch apply --verify --match work/myfork/patches/src/ui/window.cc.hatch
```

Конфиг файла находится по заявке: сначала вверх от файла до корня его репозитория; затем
в непосредственных подпапках каждого корня репозитория на пути вверх
(`work/*/hatch.config.json`) и в папках выше репозитория. Два конфига, заявляющих один
файл, — ошибка, в которой названы оба.

| раскладка | конфиг | `upstream` |
|---|---|---|
| проект внутри апстрима | `work/myfork/hatch.config.json` | `".."` |
| апстрим внутри проекта | `proj/hatch.config.json`, код в `proj/upstream/` | `"upstream"` |
| рядом | `ws/proj/hatch.config.json`, код в `ws/upstream/src/` | `"../upstream/src"` — запуск из `ws/proj` или `--config` / `$HATCH_CONFIG` |
| один репозиторий, патчи отдельным деревом | в корне репозитория | `"."` |
| один репозиторий, патч рядом с файлом или в одной папке | в корне репозитория | нет |

`hatch init --upstream ..` пишет такой конфиг. `"upstream": "."` — то, чем был
`generate.mirror`.

`generate.base` (схема 2) один раз на проект называет старую версию — так же, как
`--head`, `--branch` и `--commit` на один запуск: `{ "head": true }` — последний коммит
здесь, `{ "branch": "main" }` — вершина `main`, `{ "commit": "v1.0" }` — этот тег. С ним
`hatch generate --in <файл>` не нужен флаг источника. Любой git-флаг заменяет все три на
этот запуск, а `--in-old` их не замечает. `generate.base.eol: "worktree"` читает эту
версию с окончаниями строк файла на диске (`--eol`) — для `core.autocrlf`.

```
--config <файл>         взять этот конфиг вместо поиска вверх по дереву; явный
                        путь ничем не ограничен — так один конфиг делится между
                        несколькими репозиториями
--no-config             игнорировать конфиг-файлы (только дефолты и флаги)
--print-config          напечатать итоговые настройки, файл, из которого они
                        взяты, и происхождение каждой
```

Настраивается только сторона **generate**. `.hatch`-патч — публичный контракт и
обязан значить одно и то же на любой машине, поэтому всё, что меняет ЧТЕНИЕ
готового патча (`apply`), в конфиг не выносится никогда — такое записывается
внутрь самого `.hatch`. Неизвестный ключ — ошибка (код `5`), а не молчаливый
дефолт.

Когда патч не ложится, быстрее всего понять причину так: `--debug` у `generate`
показывает, как выбирались якоря, а `--dry-run` у `apply` — какие ровно правки
получились бы, не трогая файл.

### Коды выхода (для CI)
`0` успех · `2` ошибка разбора · `3` нет совпадения (показывает «самую глубокую»
точку, до которой дошёл шаблон) · `4` неоднозначно (показывает конкурирующие
позиции) · `5` негодная конфигурация · `6` грамматики нет или она не сошлась с
пином · `7` `generate` не нашёл, что менять: новая версия совпадает со старой после
нормализации (одни пробелы и пустые строки — не изменение), а с `--exact` — побайтно;
`.hatch` не записан · `8` `generate` не смог привязать правку: ни один шаблон вокруг неё не
ложится туда и только туда (в терминале сначала предлагается редактор) · `1` всё остальное: неверный вызов, нет файла, отказ git, неизвестный язык,
ответ «нет» на вопрос или непредвиденный сбой.

Неоднозначность — **ошибка**, а не молчаливый выбор: если шаблон ложится в двух
местах с разным результатом, будет код `4` и список позиций, а лечится это
добором контекста.

## Применение патчей при сборке: `hatch-apply`

Сборке проекта не должны быть нужны Node, npm и сеть, чтобы наложить патчи на код. В каждом
выпуске есть `hatch-apply` — один исполняемый файл, внутри которого Node, рантайм
tree-sitter и все закреплённые грамматики, — для linux-x64, linux-arm64, darwin-arm64 и
win-x64, и рядом `SHA256SUMS`. Движок тот же, что у `hatch apply`: патч, который
`generate` сделал и который ложится в редакторе, ляжет и при сборке.

```bash
curl -LO https://github.com/Danil-Varakin/hatchTs/releases/download/v0.4.0/hatch-apply-0.4.0-linux-x64
curl -LO https://github.com/Danil-Varakin/hatchTs/releases/download/v0.4.0/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
install -m755 hatch-apply-0.4.0-linux-x64 tools/hatch-apply

tools/hatch-apply verify --match myfork/patches/src/ui/window.cc.hatch
tools/hatch-apply apply  --match myfork/patches/src/ui/window.cc.hatch
```

| | |
|---|---|
| `hatch-apply apply --match <патч> [--out <путь>]` | накладывает патч на его файл — без `--out` на месте |
| `hatch-apply verify --match <патч>` | то же без записи: код 0, если ложится чисто |
| `hatch-apply --version` | версия, Node внутри, пин каждой грамматики |

Файл — тот, что патч называет в `Target`, найденный через `hatch.config.json` проекта так
же, как его находит `hatch` (`--in` называет другой). База всегда чистая: из git —
`--head` / `--branch` / `--commit`, иначе `generate.base` конфига — или, с
`--base-from-disk`, файлы на диске как есть (и он предупреждает, что взял их так); это
должна быть чистая база, а не файлы, на которые патч уже наложен (см. «Известные
ограничения»). Без этого — остановка с кодом 5. Он **ничего не спрашивает**: то, о чём спросил бы `hatch`
(тег вместо ветки, коммит не из названной ветки), отклоняется с объяснением. На месте
файл, где результат уже лежит, не перезаписывается — сборка его не перекомпилирует; файл
со своими изменениями — например, результат патча, который с тех пор поменялся, —
перезаписывается, и об этом сказано: код, который сборка патчит, проекту хранить не нужно.
Его флаги выбраны из флагов `hatch apply`, у каждого тот же смысл; генерации, сервиса и
загрузки в нём нет. Для базы из git нужен `git` в `PATH`.

## API

```ts
import { applyAll, synthesize, parseHatchFile, printHatchFile, adapterForLanguage } from 'hatch';

const adapter = adapterForLanguage('cpp');
await adapter.init();

const { source, edits } = applyAll(oldCode, parseHatchFile(md), adapter);
const md2 = printHatchFile(synthesize(oldCode, newCode, adapter), 'cpp');
```

### Функции

| | |
|---|---|
| `applyAll(source, file, adapter)` | применяет ханки по очереди; возвращает `{ source, edits }`. Бросает `MatchError` или `AmbiguityError` на первом ханке, который не лёг |
| `synthesize(old, new, adapter, options?)` | порождает `Hunk[]` из двух версий файла. Бросает `SynthesisError`, если правку не привязать |
| `parseHatchFile(text)` | `.hatch` → `HatchFile` |
| `printHatchFile(hunks, language?)` | `Hunk[]` → `.hatch` |
| `trailingSpaceWarnings(hunks)` | строки тела патча со значащими хвостовыми пробелами |
| `adapterForLanguage(name)` | адаптер по имени языка |
| `adapterForFile(path)` | адаптер по расширению файла |
| `supportedLanguages` | имена и синонимы языков реестра |

`adapter.init()` вызывается один раз и грузит грамматику; `buildMap` после этого
синхронный.

### Ошибки

`HatchError` — общий предок, у каждого наследника поле `exitCode`, совпадающее с
кодом выхода CLI: `ParseError` (2), `MatchError` (3), `AmbiguityError` (4),
`ConfigError` (5), `GrammarError` (6).

### Типы

`HatchFile`, `Hunk`, `MatchPattern`, `LanguageAdapter`, `ApplyResult`,
`AppliedEdit`, `SynthOptions`, `SynthEvent`, `Tracer`.

### Границы

Экспортируется только перечисленное выше. Матчер, патчер, канонизатор, карта
исходника, `infra/` и содержимое папок языков — внутренние и меняются без
предупреждения; подпути (`hatch/dist/...`) закрыты полем `exports`.

`LanguageAdapter` доступен как тип: адаптер получают из реестра и передают
обратно. Написание своих адаптеров не поддерживается.

## Сервис: hatch для редактора

`node node_modules/hatch/dist/bin/service.js` запускает hatch долгоживущим процессом,
который говорит JSON по stdio: `generate`, `resolve` и `apply` над текстом вместо
файлов, и координаты каждого ханка в базе и в пропатченном тексте. С ним говорит
расширение VS Code. Контракт и то, как сверяется его версия, — в
[PROTOCOL.md](./PROTOCOL.md) (на английском); типы опубликованы как `hatch/protocol`.

## Грамматики

Разбор делает tree-sitter, поэтому каждому языку нужен свой `.wasm`. Грамматики **идут
внутри hatch** — около 17 МБ на все, 1,7 МБ в упакованном архиве, — и во время работы
ничего не скачивается. Каждый язык пинует свою грамматику в собственной папке:

```ts
grammar: {
  file: 'tree-sitter-go.wasm',
  package: 'tree-sitter-go',
  version: '0.25.0',
  sha256: '9504573f352b20be7f2f1911754d710622aedc15afff16d5ed8fb5645681aee7',
},
```

и байты обязаны совпасть с пином, где бы файл ни нашёлся: `.wasm` — исполняемый код, а
другая грамматика может положить ханк в другое место (F3), поэтому файл с другим sha256
роняет запуск (код `6`). Грамматики нет совсем — это сбой сборки, так и сказано.

| Переменная | Действие |
|---|---|
| `HATCH_GRAMMAR_DIR` | искать сначала здесь — работа над ядром, своя сборка; пин всё равно проверяется |

В репозитории грамматик нет: `npm run grammars` (`scripts/fetch-grammars.ts`) кладёт
закреплённые в `grammars/`, его запускают `npm test` и `npm pack`.
`node --experimental-strip-types scripts/fetch-grammars.ts --pin <пакет@версия>` печатает
блок для `index.ts` нового языка.

До 0.3 грамматики качались в кеш пользователя командой `hatch grammars` или флагом
`--download-grammars`. В 0.4 оба работают, ничего не делают и предупреждают; в 0.5
удаляются. `HATCH_GRAMMAR_CACHE` и `HATCH_GRAMMARS_DOWNLOAD` больше ничего не делают.

## Три правила, зафиксированные волевым актом (из синтаксиса не выводятся)

Они осознанные и стабильные; патчи на них опираются:

1. **`<<<` заменяет ВКЛЮЧИТЕЛЬНО.** Литералы между `>>>` и `<<<` — это «старый
   код»: обязаны совпасть, но в выход не идут — их место занимает тело патча.
   Литералы *снаружи* меток — контекст, сохраняются.
2. **Шаблон описывает файл целиком.** `...` — единственный способ что-то
   пропустить. Нет ведущего `...` — первый якорь стоит со смещения 0; нет
   хвостового — последний якорь кончается на EOF.
3. **Незакрытая `{` упорядочивает, но не запирает.** Совпавшая открывающая скобка
   означает лишь «следующий якорь — после неё»: поиск всё равно идёт до конца
   файла, и «побег» из блока легален. Чтобы удержать правку **внутри**
   конструкции, в шаблоне надо написать её закрывающий токен. Поэтому `generate`
   выдаёт и заголовок охватывающей функции, и её `}`.

## Известные ограничения

Чего hatch не делает — намеренно или пока, — и что стоит знать заранее:

- **Одинаковый код с одинаковым окружением не различить.** В языке шаблонов нет
  «n-го вхождения»: если два места совпадают слово в слово вместе с соседями,
  `generate` сообщит о неоднозначности, а `apply` выйдет с кодом `4`. Такой якорь
  пишется руками — с опорой на отличающийся код, часто на тот, что идёт *после* правки.
- **«Уже применено» не распознаётся — его исключает порядок работы.** hatch не проверяет,
  есть ли патч в файле: нашёл место — пишет. Наложенный второй раз на собственный
  результат, патч может повторить вставку с кодом 0 — `... void g() { ... >>> } ...`
  по-прежнему находит конец `g()`; на не том файле обычно выходит код `3`. Поэтому каждый
  запуск, который что-то решает, начинается с чистой базы: `apply --verify` и
  `hatch-apply` читают файл из git (`--head`, `--branch`, `--commit` или `generate.base`),
  а `generate` проверяет каждый ханк на той старой версии, что ему дали. Патчить файлы
  на диске (`hatch apply` без git-координаты, `--base-from-disk`) можно только когда они и
  есть эта чистая база, — никогда файл, на который патч уже наложен.
- **Окончания строк принадлежат файлу, а не патчу.** Патч пишет строки с окончанием той
  строки, где начинается правка, поэтому перевести CRLF-строки в LF (и обратно) патчем,
  начинающимся на CRLF-строке, нельзя.
- **Git с `core.autocrlf=true`** (умолчание Git for Windows): версия из git приходит с
  окончаниями, которые хранит репозиторий (LF), а файл на диске — с CRLF, и
  `generate --head --exact` видит изменённой каждую строку. Добавьте `--eol worktree`
  (или `generate.base.eol: "worktree"` в конфиге) — версия из git придёт с окончаниями
  файла на диске; либо поставьте для репозитория `core.autocrlf false` (так велит и
  настройка Chromium под Windows), либо передайте старую версию через `--in-old`.
- **Большие файлы из почти одинакового кода замедляют `generate`** — от секунд до минут
  там, где один шаблон приходится примерять к множеству похожих мест.
- **При записи файла сохраняются права и запись идёт сквозь симлинк**, но не владелец,
  ACL и расширенные атрибуты, а жёсткая ссылка на файл отделяется — запись идёт через
  временный файл и переименование, чтобы прерванный запуск не оставил полфайла.
- **Пробелы внутри многострочного строкового литерала не значимы** (см. «Язык»), а
  `.mm` читается грамматикой Objective-C (см. «Поддержка языков»).

## Поддержка языков

Языки, на которых написан Chromium:

| Язык | Расширения | Имя в заголовке / `--language` |
|------|-----------|--------------------------------|
| C++ | `.cc` `.cpp` `.cxx` `.h` `.hpp` `.inc` | `cpp`, `c++`, `cc`, `cxx`, `h`, `hpp` |
| C | `.c` | `c` |
| Objective-C | `.m` `.mm` | `objc`, `objective-c` |
| Python | `.py` `.pyi` | `python`, `py` |
| JavaScript (с JSX) | `.js` `.mjs` `.cjs` `.jsx` | `javascript`, `js`, `jsx` |
| TypeScript | `.ts` `.mts` `.cts` | `typescript`, `ts` |
| TSX | `.tsx` | `tsx` |
| Rust | `.rs` | `rust`, `rs` |
| Java | `.java` | `java` |
| Kotlin | `.kt` `.kts` | `kotlin`, `kt` |
| Go | `.go` | `go`, `golang` |

`generate` пишет в заголовок собственное имя языка — первое в последней колонке
(`cpp`, `objc`, `python`), как бы язык ни был выбран. Любое расширение из таблицы без
точки — тоже имя: его писал hatch 0.2.0 и старше (`# match mm`), и такой `.hatch`
применяется так же.

Структура берётся из tree-sitter, поэтому ветки препроцессора, raw-строки, макросы
и дженерики (`Map<K, V>` — пара скобок, `a < b` — нет) не путают сопоставление.
`.h` считается C++ по конвенции Chromium. `.mm` — это Objective-C++, которого не
покрывает полностью ни одна грамматика tree-sitter: лучше всех справляется
грамматика Objective-C, а на чисто C++-участках структура беднеет до текстового
сопоставления.

### Как добавить язык: правило одной папки

**Язык — это одна папка в `src/lang/` и один `index.ts` в ней, где лежат ВСЕ его
правила: какую грамматику грузить, какие расширения считать своими, как
балансировать вложенность (`blockOf`) и как канонизировать текст литерала
(`normalize`). Правила языков НЕ выносятся в общий модуль — даже когда у двух
языков они записались бы дословно одинаково.**

Что это даёт: чтобы добавить язык, вы копируете одну папку и правите один файл,
ничего не зная про остальные и ничего в них не задевая. Видимое дублирование —
осознанная цена, и на практике правила расходятся: наборы скобочных пар у C, Go,
JavaScript и Python уже разные, а Kotlin требует своего определения того, где
начинается заголовок блока. Общий модуль «правил C-подобных» превратил бы каждое
такое различие в флаг.

Общим остаётся только язык-НЕЙТРАЛЬНОЕ: загрузка грамматики, обход дерева,
обвязка канона, сборка карты — то, чего язык не выбирает. Единственный общий файл,
который затрагивает добавление языка, — реестр адаптеров, и только потому, что
whitelist обязан быть статическим списком: имя языка приходит из недоверенного
`.hatch` и не должно превращаться в динамический импорт.

В `src/core/` при этом тоже не меняется ничего — это вторая проверка границы, и ни
одному языку из таблицы исключений не потребовалось. Python среди них стоит
особняком: значимый отступ, поэтому у него свой канонизатор и своё понятие блока,
где открывающий токен — двоеточие.

Грамматики лежат в `grammars/*.wasm`, их кладёт туда из официальных npm-пакетов
tree-sitter `npm run grammars`, и они идут внутри пакета.

## Сборка и запуск

Исходники — `.ts`, исполняются напрямую на **Node 22+** через strip-types, поэтому
разработке шаг сборки не нужен. Пакет для публикации собирается (`npm run build` →
`dist/`), и именно эта сборка попадает в архив `npm pack`.

```bash
npm test          # юнит-, round-trip- и golden-наборы
npm run typecheck # tsc --noEmit по src/ и test/
npm run check     # то и другое
npm run build     # dist/, только для пакета
```

Разбор структуры — через **tree-sitter** (`web-tree-sitter`, WASM-грамматики:
кросс-платформенно, без нативной сборки); грузятся разово на старте. Рабочий
процесс и обоснование строгого tsconfig — в [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md).
